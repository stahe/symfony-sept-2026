    5. Internationalisation

    Une application internationalisée affiche ses textes dans la langue de l'utilisateur. L'étude de cas est en français et en anglais. Le principe est simple : les vues ne contiennent plus de textes, mais des clés ([MENU.ACCUEIL]), et un dictionnaire par langue associe à chaque clé son texte. La langue choisie est mémorisée dans un cookie.

    [Symfony] possède un composant de traduction, le Translator, déjà rencontré à l'exemple 09 pour les messages de validation. Ses dictionnaires sont rangés dans le dossier [translations], un fichier par domaine et par langue : [validators.fr.yaml] (le domaine des messages de validation, exemple 09), [messages.fr.yaml] (le domaine par défaut, celui de nos textes). Le format YAML permet d'imbriquer les clés : c'est la présentation des dictionnaires des versions [ASP.NET Core MVC], [NestJS], [Spring MVC], [Flask] et [Laravel] de l'étude de cas, à la syntaxe près. Pour la syntaxe des messages eux-mêmes, nous choisissons le format ICU (International Components for Unicode), une norme que l'extension [intl] de [PHP] sait interpréter, et qui sait par exemple accorder un texte au pluriel. La mise en forme des dates et des montants reste celle de l'exemple 16.

PRODUITS:

    NOM: Produit
    PRIX: Prix

    Le nom du fichier est fait de trois parties : le domaine ([messages], le domaine par défaut), le suffixe [+intl-icu], qui annonce des messages au format ICU, et la langue ([fr]). Les clés sont regroupées par thème grâce à l'imbrication du YAML : le texte « Accueil » du menu a pour clé [MENU.ACCUEIL], les niveaux étant séparés par un point. Un texte peut contenir des paramètres, écrits [{nom}], remplacés au moment de la traduction.

    • ligne 9 : les apostrophes délimitent une chaîne YAML ; elles sont nécessaires quand le texte contient des caractères que YAML interprète (accolades, deux-points...) ;
    • ligne 15 : un message au pluriel. [{n, plural, ...}] choisit une forme selon la valeur du paramètre [n] : [=0] pour la valeur 0 exactement, [one] pour le singulier, [other] pour le pluriel ; [#] est remplacé par le nombre. Les règles du pluriel dépendent de la langue, et ICU les connaît : en français, 0 et 1 sont au singulier, alors qu'en anglais 0 est au pluriel (« 0 products »). C'est un progrès sur le « produit(s) » des versions précédentes de l'étude de cas.

    <?php
// src/EventListener/DefinirLangue.php : la langue de chaque requête

namespace App\EventListener;

use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\HttpKernel\Event\RequestEvent;
use Symfony\Component\HttpKernel\KernelEvents;

// priorité 20 : après le routage, avant les écouteurs de Symfony qui utilisent la langue (cf. exemple 16)
#[AsEventListener(event: KernelEvents::REQUEST, priority: 20)]
class DefinirLangue
{
    // les langues gérées ; la première est la langue par défaut
    public const LANGUES = ['fr', 'en'];

    public const COOKIE = 'langue';

    // la langue du cookie [langue] si elle est gérée, le français sinon
    public function __invoke(RequestEvent $evenement): void
    {
        $requete = $evenement->getRequest();
        $langue = $requete->cookies->get(self::COOKIE);
        $requete->setLocale(in_array($langue, self::LANGUES, true) ? $langue : self::LANGUES[0]);
    }
}

    C'est l'écouteur [FixerLangue] de l'exemple 16, qui prend cette fois la langue dans un cookie :

    • ligne 11 : l'écouteur de l'événement [kernel.request], avec la priorité 20 : après le routage, mais avant les écouteurs de [Symfony] qui utilisent la langue de la requête (exemple 16) ;
    • lignes 15-17 : les langues gérées, et le nom du cookie : des constantes de classe publiques, accessibles depuis les autres classes ([DefinirLangue::LANGUES]) ;
    • lignes 22-24 : la langue de la requête : celle du cookie [langue] s'il en existe un et qu'elle est gérée, le français sinon. [$requete->cookies] est l'ensemble des cookies envoyés par le navigateur (exemple 05) ; [get] rend la valeur d'un cookie, ou [null]. [in_array], avec [true] en troisième paramètre, compare aussi les types ([===]). [setLocale] fixe la langue de la requête : c'est celle qu'utilisent le traducteur, nos filtres de mise en forme, et le filtre [format_currency] de [Twig].

    Contrairement à [Laravel], [Symfony] ne chiffre pas les cookies : le cookie [langue] circule en clair. Ce n'est pas un problème : il ne contient rien de secret, et le serveur n'accepte que les langues gérées. L'exemple suivant revient sur la confiance qu'on peut accorder à un cookie.

    <?php
// src/Controller/LangueController.php : le choix de la langue

namespace App\Controller;

use App\EventListener\DefinirLangue;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\RedirectResponse;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\Routing\Attribute\Route;

class LangueController extends AbstractController
{
    // GET /langue/en : mémorise le choix dans un cookie, puis revient à la page précédente.
    // requirements : une autre langue que fr ou en ne correspond pas à la route (404)
    #[Route('/langue/{code}', name: 'langue', requirements: ['code' => 'fr|en'], methods: ['GET'])]
    public function changer(Request $request, string $code): RedirectResponse
    {
        $reponse = $this->redirect(self::pageDOrigine($request));
        // le cookie : un an de vie, illisible par le JavaScript de la page (httpOnly),
        // jamais envoyé avec une requête POST venue d'un autre site (sameSite lax)
        $reponse->headers->setCookie(Cookie::create(DefinirLangue::COOKIE, $code)
            ->withExpires(new \DateTimeImmutable('+1 year'))
            ->withHttpOnly(true)
            ->withSameSite(Cookie::SAMESITE_LAX));
        return $reponse;
    }

    // la page d'où l'on vient (entête Referer), dont on ne garde que le chemin :
    // rediriger vers une adresse complète venue de la requête permettrait
    // d'envoyer l'utilisateur sur un autre site (faille "open redirect")
    private static function pageDOrigine(Request $request): string
    {
        // parse_url découpe une URL en ses composants (chemin, paramètres...)
        $url = parse_url($request->headers->get('Referer', ''));
        $chemin = $url['path'] ?? '';
        // "//site.com/..." serait compris par le navigateur comme une adresse
        // sur un AUTRE site : refusé aussi
        if (! str_starts_with($chemin, '/') || str_starts_with($chemin, '//')) {
            return '/';
        }
        return isset($url['query']) ? "$chemin?{$url['query']}" : $chemin;
    }
}
    • ligne 17 : la route [/langue/{code}]. L'option [requirements] (exemple 02) limite le paramètre aux deux langues gérées : [/langue/de] ne correspond à aucune route, et donne une erreur 404 ;
    • ligne 20 : l'action répond par une redirection vers la page d'où vient l'utilisateur : celui-ci retrouve sa page, dans la nouvelle langue ;
    • lignes 23-26 : la réponse porte un cookie, que le navigateur renverra à chaque requête. La classe [Cookie] de [Symfony] le décrit : [Cookie::create(nom, valeur)] le fabrique, et chaque méthode [with...] rend une copie modifiée (un objet immuable, cf. exemple 03) : [withExpires], la date d'expiration (dans un an) ; [withHttpOnly(true)] le rend invisible au [JavaScript] de la page ; [withSameSite(Cookie::SAMESITE_LAX)] interdit au navigateur de l'envoyer avec une requête POST venue d'un autre site. ([httpOnly] et [lax] sont d'ailleurs les valeurs par défaut de [Cookie::create].) [$reponse->headers->setCookie] l'ajoute à la réponse, sous la forme d'un entête [Set-Cookie] ;
    • lignes 33-44 : la page d'origine est donnée par l'entête [Referer] de la requête (l'orthographe fautive, avec un seul [r], est celle de la norme HTTP), que le navigateur remplit avec l'URL de la page qui contenait le lien. Mais cet entête vient du client, qui peut y mettre n'importe quoi. Rediriger aveuglément vers cette adresse ferait de notre application un redirecteur ouvert (open redirect) : un lien piégé, qui porte notre nom de domaine, pourrait envoyer l'utilisateur sur un site malveillant. On ne garde donc que le chemin et les paramètres de l'URL (la fonction [parse_url] de [PHP] la découpe en ses composants, dans un tableau associatif), et l'on refuse un chemin qui commence par [//], que le navigateur comprendrait comme l'adresse d'un autre site.

namespace App\Controller;

use App\Modele\Produit;
use DateTimeImmutable;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

#[Route(methods: ['GET'])]
class PagesController extends AbstractController
{
    #[Route('/', name: 'accueil')]
    public function accueil(): Response
    {
        return $this->render('pages/accueil.html.twig', ['nom' => 'Marie',
            'aujourdhui' => new DateTimeImmutable('2026-09-23')]);
    }

    #[Route('/produits', name: 'produits')]
    public function produits(): Response
    {
        return $this->render('pages/produits.html.twig', ['produits' => [
            new Produit('Clavier', 2500),
            new Produit('Souris', 1250),
            new Produit('Écran', 114900),
        ]]);
    }
}

    Les actions ne savent rien de la langue : elles fournissent des données brutes (un nom, une date, des montants en centimes). La traduction et la mise en forme sont l'affaire des vues. La classe [Produit] a un nom et un prix en centimes ; l'extension [FormatsExtension] est celle de l'exemple 16 : son filtre [date_longue] écrit une date au format « complet » de la langue de la requête (« mercredi 23 septembre 2026 », « Wednesday, September 23, 2026 »), et son filtre [monnaie] un montant.
