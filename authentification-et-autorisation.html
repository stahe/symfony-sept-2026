    8. Authentification et autorisation

    Deux questions distinctes se posent pour chaque requête :

    • qui est l'utilisateur ? C'est l'authentification : il s'est identifié par un login et un mot de passe, et chaque requête suivante doit prouver qu'elle vient de lui ;
    • a-t-il le droit d'accéder à cette page ? C'est l'autorisation : dans l'étude de cas, seul un utilisateur de rôle ADMIN gère les médecins et les clients.

    La preuve d'identité doit voyager avec chaque requête. [Symfony] range d'ordinaire l'utilisateur connecté dans sa session (chapitre sur les portées), ce qui est la solution la plus simple pour une application web. L'étude de cas, dans toutes ses versions ([ASP.NET Core MVC], [Spring MVC], [NestJS], [Flask], [Laravel]), utilise plutôt un jeton JWT (JSON Web Token), que nous garderons ici : après la connexion, le serveur fabrique un jeton qui contient l'identité de l'utilisateur et le signe avec une clé secrète (c'est le principe du cookie signé de l'exemple 23). Le jeton est déposé dans un cookie ; le navigateur le renvoie à chaque requête ; le serveur vérifie la signature. L'utilisateur peut lire son jeton, mais pas le modifier : toute modification rend la signature invalide. Le format est normalisé (RFC 7519), compris par tous les langages, et le jeton porte sa date d'expiration. Surtout, le serveur n'a rien à mémoriser : n'importe quel serveur qui connaît la clé peut vérifier le jeton.

    [Symfony] possède un composant de sécurité complet, intégré par le SecurityBundle, dont les éléments nous serviront tels quels :

    • les URL de l'application sont réparties entre des pare-feu (firewalls), chacun avec sa façon d'authentifier les utilisateurs ;
    • l'authentification est confiée à des authentificateurs (authenticators) : des objets qui, pour chaque requête, établissent qui est l'utilisateur. [Symfony] en fournit plusieurs (formulaire de connexion, session, jeton d'API...) ; nous écrirons le nôtre, qui lit le jeton JWT. Le reste de l'application ne voit que le résultat : l'utilisateur authentifié, que donnent [#[CurrentUser]], [$this->getUser()] et, dans les vues, [app.user] ;
    • les utilisateurs sont fournis par un fournisseur d'utilisateurs (user provider), et leurs mots de passe hachés par le composant PasswordHasher (algorithme [bcrypt]) ;
    • les autorisations reposent sur des rôles : la protection des pages est décrite par des règles de contrôle d'accès ([access_control]) ou par l'attribut [#[IsGranted]] des actions ; les vues testent un droit par [is_granted] ;
    • les tentatives de connexion sont limitées par le composant RateLimiter (exemple 27).

    Tout cela est réalisé par des écouteurs des événements du noyau (chapitre précédent) : le pare-feu écoute [kernel.request] (priorité 8), [#[IsGranted]] est lu sur [kernel.controller_arguments], et les refus d'accès sont des exceptions, traitées sur [kernel.exception].

    La fabrication et la vérification des jetons sont confiées à la bibliothèque [firebase/php-jwt], la plus utilisée en [PHP], installée par le fichier [composer.json] des exemples. (Il existe un bundle très utilisé pour les jetons JWT, [LexikJWTAuthenticationBundle], conçu pour les API ; pour une application web, quelques lignes suffisent, et elles montrent mieux le mécanisme.)

    8.1.1. La configuration : .env, bundles.php et framework.yaml

    Le jeton est signé avec une clé secrète, qui ne doit pas être écrite dans le code. Il est temps de séparer vraiment la configuration du code. Les réglages propres à une installation sont dans le fichier [.env] (exemple 01), qui reçoit trois nouvelles lignes (un commentaire, puis deux variables) :

Le code, lui, ne lit pas le fichier [.env] directement : le composant [Dotenv] (exemple 01) en a fait des variables d'environnement, que le conteneur fournit aux services qui les demandent (nous le verrons avec le service [AuthService]). Une vraie variable d'environnement l'emporte sur le fichier [.env] : sous [Linux] ou [macOS], on lancerait l'application avec une autre clé ainsi :

    JWT_SECRET="une-autre-cle-d-au-moins-trente-deux-caracteres" php -d variables_order=EGPCS -S localhost:8000 -t public

    et sous [Windows] (PowerShell) :

    1
2
    $env:JWT_SECRET="une-autre-cle-d-au-moins-trente-deux-caracteres"
php -d variables_order=EGPCS -S localhost:8000 -t public

En production, les secrets sont souvent confiés au coffre de [Symfony] (secrets vault, commande [bin/console secrets:set]), qui les range chiffrés dans le projet.

// src/Securite/UtilisateursService.php : les utilisateurs, en mémoire (l'exemple 28
// et l'étude de cas les mettront dans une base). UserProviderInterface : un
// FOURNISSEUR d'utilisateurs, au sens de Symfony (cf. config/packages/security.yaml)

namespace App\Securite;

use Symfony\Component\Security\Core\Exception\UnsupportedUserException;
use Symfony\Component\Security\Core\Exception\UserNotFoundException;
use Symfony\Component\Security\Core\User\UserInterface;
use Symfony\Component\Security\Core\User\UserProviderInterface;

class UtilisateursService implements UserProviderInterface
{
    // on ne conserve JAMAIS un mot de passe, seulement son hachage bcrypt, calculé
    // une fois pour toutes par : php -r "echo password_hash('marie', PASSWORD_BCRYPT);"
    private const UTILISATEURS = [
        'marie' => ['Marie Pélissier', 'USER', '$2y$10$2DnOgGBiVcyc07su9rj2E.EvOoyPFzHN/h9PLKDuoW5P7UGtclW6W'],
        'admin' => ['Administrateur', 'ADMIN', '$2y$10$m5o9euCi0EdgoZkLVw.UsO58RxJcqhMBfVrlLMCIOh2LyGSjuN29K'],
    ];

    public function chercher(string $login): ?Utilisateur
    {
        if (! isset(self::UTILISATEURS[$login])) {
            return null;
        }
        [$nom, $role, $hachage] = self::UTILISATEURS[$login];
        return new Utilisateur($login, $nom, $role, $hachage);
    }

    // les trois méthodes de UserProviderInterface
    public function loadUserByIdentifier(string $identifier): UserInterface
    {
        return $this->chercher($identifier) ?? throw new UserNotFoundException();
    }

    // l'utilisateur rangé dans la session, à recharger : jamais appelée ici,
    // puisque le pare-feu est sans état
    public function refreshUser(UserInterface $user): UserInterface
    {
        throw new UnsupportedUserException();
    }

    public function supportsClass(string $class): bool
    {
        return $class === Utilisateur::class;
    }
}
    • lignes 17-20 : deux utilisateurs de test, écrits dans le code (l'exemple 28 et l'étude de cas les mettront dans une base de données) : pour chaque login, le nom, le rôle, et le hachage du mot de passe. Le hachage est celui de l'algorithme bcrypt, conçu pour les mots de passe. Il a deux particularités. Il est volontairement lent, d'une lenteur réglable (le coût, ici 10 : 2^10 tours de calcul, le [$10$] du hachage) : quelques dizaines de millisecondes, imperceptibles pour un utilisateur, mais qui rendent très coûteux l'essai de milliards de mots de passe par un pirate. Il est salé : un sel, tiré au hasard, est mélangé au mot de passe avant hachage, et rangé dans le hachage lui-même (les 22 caractères qui suivent [$10$]) ; deux utilisateurs qui ont le même mot de passe ont ainsi des hachages différents. Les hachages ont été calculés une fois pour toutes, par la fonction [password_hash] de [PHP] (ligne 16), ou par la commande [bin/console security:hash-password] de [Symfony] : les calculer à chaque requête coûterait inutilement du temps, puisque l'application est reconstruite à chaque requête. [bcrypt] ne prend en compte que les 72 premiers octets d'un mot de passe : l'étude de cas en tient compte ;
    • lignes 22-29 : l'utilisateur d'un login, ou [null]. [isset] teste l'existence d'une clé ; l'affectation [[$nom, $role, $hachage] = ...] déstructure un tableau : chaque variable reçoit l'élément correspondant ;
    • lignes 32-47 : les trois méthodes de l'interface [UserProviderInterface], qui font de la classe un fournisseur d'utilisateurs : [loadUserByIdentifier] rend l'utilisateur d'un identifiant, ou lève l'exception [UserNotFoundException] ; [refreshUser] recharge l'utilisateur rangé dans la session (inutile avec un pare-feu sans état) ; [supportsClass] indique la classe des utilisateurs fournis. L'opérateur [??] suivi de [throw] lève l'exception quand l'expression de gauche vaut [null].

    <?php
// src/Securite/AuthService.php : la vérification des mots de passe et les jetons JWT

namespace App\Securite;

use Firebase\JWT\JWT;
use Firebase\JWT\Key;
use Symfony\Component\DependencyInjection\Attribute\Autowire;
use Symfony\Component\PasswordHasher\Hasher\UserPasswordHasherInterface;
use Throwable;

class AuthService
{
    // le nom du cookie qui transporte le jeton
    public const COOKIE = 'jeton';

    public function __construct(
        private UtilisateursService $utilisateurs,
        // le service de hachage des mots de passe (cf. config/packages/security.yaml)
        private UserPasswordHasherInterface $hacheur,
        // #[Autowire(env: ...)] : la valeur d'une variable d'environnement (fichier .env) ;
        // le préfixe int: la convertit en entier
        #[Autowire(env: 'JWT_SECRET')] private string $secret,
        #[Autowire(env: 'int:JWT_DUREE_MINUTES')] public readonly int $dureeMinutes,
    ) {
    }

    // l'utilisateur, ou null si le login est inconnu ou le mot de passe faux.
    // isPasswordValid hache le mot de passe saisi avec le sel du hachage enregistré,
    // puis compare les deux résultats
    public function valider(?string $login, ?string $motDePasse): ?Utilisateur
    {
        if (! $login || $motDePasse === null) {
            return null;
        }
        $utilisateur = $this->utilisateurs->chercher($login);
        if ($utilisateur === null || ! $this->hacheur->isPasswordValid($utilisateur, $motDePasse)) {
            return null;
        }
        return $utilisateur;
    }

    // le jeton JWT de l'utilisateur, signé avec la clé secrète (HMAC-SHA256)
    public function creerJeton(Utilisateur $utilisateur): string
    {
        $maintenant = time();
        // le contenu du jeton : les "claims" (affirmations sur l'utilisateur)
        $claims = [
            'sub' => $utilisateur->login,
            'nom' => $utilisateur->nom,
            'role' => $utilisateur->role,
            'iat' => $maintenant,
            'exp' => $maintenant + $this->dureeMinutes * 60,
        ];
        return JWT::encode($claims, $this->secret, 'HS256');
    }

    // l'utilisateur décrit par un jeton dont la signature et la date d'expiration
    // sont valides ; null sinon (jeton falsifié, expiré ou illisible)
    public function verifier(string $jeton): ?Utilisateur
    {
        try {
            // decode rend un objet ; (array) le convertit en tableau associatif
            $claims = (array) JWT::decode($jeton, new Key($this->secret, 'HS256'));
        } catch (Throwable) {
            return null;
        }
        return new Utilisateur($claims['sub'], $claims['nom'], $claims['role'], claims: $claims);
    }
}
    • lignes 17-26 : le service reçoit le fournisseur d'utilisateurs, le service de hachage des mots de passe ([UserPasswordHasherInterface], qui applique l'algorithme choisi dans [security.yaml]), et deux valeurs de configuration. L'attribut [#[Autowire(env: 'NOM')]] fournit la valeur d'une variable d'environnement ; un préfixe la convertit : [int:] en entier (il en existe d'autres : [bool:], [json:], [base64:]...). La durée de vie est une propriété publique en lecture seule : le contrôleur s'en servira ;
    • lignes 31-41 : la vérification d'un login et d'un mot de passe. [isPasswordValid] hache le mot de passe saisi avec le sel du hachage enregistré, et compare les deux hachages. Un login inconnu et un mot de passe faux donnent le même résultat, [null] ;
    • lignes 44-56 : la fabrication du jeton. Son contenu est un tableau d'affirmations (claims) sur l'utilisateur. Certaines ont un nom normalisé : [sub] (subject), l'identifiant de l'utilisateur ; [iat] (issued at), la date de création ; [exp] (expiration), la date d'expiration. Les dates s'écrivent en secondes écoulées depuis le 1er janvier 1970 (la fonction [time()] de [PHP]). Les autres affirmations sont libres : ici le nom et le rôle. [JWT::encode] fabrique le jeton et le signe avec l'algorithme [HS256] (HMAC-SHA256, une signature par clé secrète partagée) ;
    • lignes 60-69 : la vérification d'un jeton. [JWT::decode] vérifie la signature et la date d'expiration, puis rend les affirmations (un objet, converti en tableau par [(array)]). Toute anomalie (jeton falsifié, expiré, mal formé) lève une exception ; [catch (Throwable)] les intercepte toutes ([Throwable] est l'interface de toutes les exceptions et erreurs de [PHP] ; le nom de variable est facultatif quand on ne l'utilise pas). L'objet [Key] associe la clé à un algorithme : un jeton qui déclarerait un autre algorithme (voire aucun, [none]) serait refusé. Le jeton valide devient un [Utilisateur], sans hachage, avec ses affirmations (paramètre nommé [claims]).

// config/packages/security.yaml) : à chaque requête, il établit qui est l'utilisateur,
// d'après le jeton JWT du cookie [jeton]

namespace App\Securite;

use Symfony\Component\HttpFoundation\RedirectResponse;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Security\Core\Authentication\Token\TokenInterface;
use Symfony\Component\Security\Core\Exception\AuthenticationException;
use Symfony\Component\Security\Core\Exception\CustomUserMessageAuthenticationException;
use Symfony\Component\Security\Http\Authenticator\AbstractAuthenticator;
use Symfony\Component\Security\Http\Authenticator\Passport\Badge\UserBadge;
use Symfony\Component\Security\Http\Authenticator\Passport\Passport;
use Symfony\Component\Security\Http\Authenticator\Passport\SelfValidatingPassport;
use Symfony\Component\Security\Http\EntryPoint\AuthenticationEntryPointInterface;

class JetonAuthenticator extends AbstractAuthenticator implements AuthenticationEntryPointInterface
{
    public function __construct(private AuthService $auth)
    {
    }

    // l'authentificateur n'agit que si la requête porte le cookie du jeton ;
    // sinon, le visiteur reste anonyme
    public function supports(Request $request): ?bool
    {
        return $request->cookies->has(AuthService::COOKIE);
    }

    // le PASSEPORT de l'utilisateur : qui il est (le badge), et comment le vérifier.
    // Le jeton a déjà été vérifié : le passeport se valide lui-même (SelfValidatingPassport)
    public function authenticate(Request $request): Passport
    {
        $utilisateur = $this->auth->verifier($request->cookies->get(AuthService::COOKIE));
        if ($utilisateur === null) {
            throw new CustomUserMessageAuthenticationException('jeton invalide');
        }
        // le badge : le login, et une fonction qui rend l'utilisateur (ici, celui du
        // jeton, sans consulter la liste des utilisateurs)
        return new SelfValidatingPassport(new UserBadge($utilisateur->login, fn () => $utilisateur));
    }

    // un jeton valide : null, la requête poursuit son chemin vers l'action
    public function onAuthenticationSuccess(Request $request, TokenInterface $token, string $firewallName): ?Response
    {
        return null;
    }

    // un jeton invalide (expiré, falsifié) : direction /login, et l'on efface le cookie
    public function onAuthenticationFailure(Request $request, AuthenticationException $exception): ?Response
    {
        $reponse = new RedirectResponse('/login');
        $reponse->headers->clearCookie(AuthService::COOKIE);
        return $reponse;
    }

    // le POINT D'ENTRÉE : la réponse faite à un visiteur anonyme qui demande une
    // page protégée ; ici, une redirection vers la page de connexion
    public function start(Request $request, ?AuthenticationException $authException = null): Response
    {
        return new RedirectResponse('/login');
    }
}

    • lignes 28-31 : [supports] : l'authentificateur est-il concerné par cette requête ? Oui si elle porte le cookie du jeton. Sinon, rien ne se passe : le visiteur reste anonyme ;
    • lignes 35-44 : [authenticate] construit un passeport : l'identité de l'utilisateur (un badge, [UserBadge]), et les preuves à vérifier. Un formulaire de connexion ordinaire mettrait dans le passeport le mot de passe saisi, que [Symfony] vérifierait lui-même. Ici, la preuve est le jeton, déjà vérifié par [AuthService] : le passeport se valide lui-même ([SelfValidatingPassport]). Le badge contient le login, et une fonction qui rend l'utilisateur : ici, celui qu'a décrit le jeton, sans consulter la liste des utilisateurs (sans cette fonction, [Symfony] demanderait l'utilisateur au fournisseur). Un jeton invalide lève une exception d'authentification ;
    • lignes 47-50 : [onAuthenticationSuccess] : l'authentification a réussi. Rendre [null] laisse la requête poursuivre son chemin vers l'action, avec un utilisateur authentifié. (Un formulaire de connexion rendrait ici une redirection vers la page d'accueil) ;
    • lignes 53-58 : [onAuthenticationFailure] : l'authentification a échoué (jeton expiré ou falsifié). La réponse redirige vers la page de connexion, et en profite pour effacer le cookie : [clearCookie] ajoute à la réponse un cookie vide, déjà expiré ;
    • lignes 62-65 : [start] est la méthode de l'interface [AuthenticationEntryPointInterface] : le point d'entrée du pare-feu, c'est-à-dire la réponse faite à un visiteur anonyme qui demande une page protégée. Ici, une redirection vers la page de connexion.

namespace App\Controller;

use App\Securite\AuthService;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Exception\AccessDeniedHttpException;
use Symfony\Component\Routing\Attribute\Route;

class AuthController extends AbstractController
{
    public function __construct(private AuthService $auth)
    {
    }

    #[Route('/', methods: ['GET'])]
    public function accueil(): Response
    {
        return $this->redirect('/profil');
    }

    #[Route('/login', methods: ['GET'])]
    public function formulaire(): Response
    {
        return $this->render('auth/login.html.twig');
    }

    #[Route('/login', methods: ['POST'])]
    public function connexion(Request $request): Response
    {
        // le jeton anti-CSRF du formulaire (cf. exemple 21)
        if (! $this->isCsrfTokenValid('login', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('jeton anti-CSRF invalide');
        }
        $login = $request->getPayload()->getString('login');
        $utilisateur = $this->auth->valider($login, $request->getPayload()->getString('motDePasse'));
        if ($utilisateur === null) {
            // un message volontairement vague : on ne dit pas si c'est le login ou le mot de passe
            return $this->render('auth/login.html.twig', ['login' => $login,
                'erreur' => 'Login ou mot de passe incorrect.']);
        }
        // le jeton, dans un cookie : le JavaScript de la page ne peut pas le lire
        // (httpOnly) ; il n'accompagne pas les requêtes POST venues d'autres sites
        // (sameSite) ; il disparaît en même temps que le jeton expire
        $reponse = $this->redirect('/profil');
        $reponse->headers->setCookie(Cookie::create(AuthService::COOKIE, $this->auth->creerJeton($utilisateur))
            ->withExpires(time() + $this->auth->dureeMinutes * 60)
            ->withHttpOnly(true)
            ->withSameSite(Cookie::SAMESITE_LAX));
        return $reponse;
    }

    // la déconnexion : POST seulement (un simple lien, placé sur un autre site, ne
    // peut pas déconnecter l'utilisateur à son insu) ; on efface le cookie
    #[Route('/logout', methods: ['POST'])]
    public function deconnexion(Request $request): Response
    {
        if (! $this->isCsrfTokenValid('logout', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('jeton anti-CSRF invalide');
        }
        $reponse = $this->redirect('/login');
        $reponse->headers->clearCookie(AuthService::COOKIE);
        return $reponse;
    }
}
    • lignes 36-38 : le formulaire de connexion est protégé contre les requêtes forgées, comme tous les formulaires (exemple 21) ;
    • lignes 40-45 : la connexion. En cas d'échec, le formulaire est réaffiché avec le login saisi et un message volontairement vague : dire « login inconnu » apprendrait à un pirate quels logins existent ;
    • lignes 49-54 : en cas de succès, le jeton est déposé dans un cookie, avec une redirection vers la page protégée (schéma PRG). Le cookie est [httpOnly] : le [JavaScript] de la page ne peut pas le lire, ce qui protège le jeton contre une injection de script (XSS) ; il est [SameSite=Lax] : le navigateur ne l'envoie pas avec une requête POST venue d'un autre site, ce qui protège l'application contre les attaques CSRF ; sa date d'expiration ([withExpires], ici un nombre de secondes depuis 1970) est celle du jeton. En production, sur HTTPS, on ajouterait [withSecure(true)] : le cookie ne serait jamais envoyé sur une connexion non chiffrée ;
    • lignes 59-68 : la déconnexion efface le cookie ([clearCookie]). C'est une action POST, protégée par un jeton anti-CSRF : un simple lien vers [/logout], placé sur un autre site ou dans une image, ne peut pas déconnecter l'utilisateur à son insu. Remarquons une limite des jetons : le jeton lui-même reste valide jusqu'à son expiration. Quelqu'un qui en aurait fait une copie pourrait encore s'en servir. C'est pourquoi on limite leur durée de vie.

    // imprévisible (contrairement à rand ou mt_rand, dont la suite pourrait être devinée)
    public static function texteAleatoire(int $longueur): string

        $texte = '';

    // un nombre à virgule, au hasard, entre $minimum et $maximum

    {
        return $minimum + ($maximum - $minimum) * random_int(0, PHP_INT_MAX) / PHP_INT_MAX;
    }

    {

    public static function svg(string $texte): string
    {

        $h = self::HAUTEUR;
        $morceaux = ["<svg xmlns=\"http://www.w3.org/2000/svg\" width=\"$l\" height=\"$h\" viewBox=\"0 0 $l $h\">",
            '<rect width="100%" height="100%" fill="#f5f7fa"/>'];

        // les caractères : chacun agrandi, penché, décalé, et chaque point
        // légèrement déplacé au hasard
        $pas = ($l - 20) / strlen($texte);
        foreach (str_split($texte) as $i => $caractere) {
            $echelle = self::hasard(4.6, 5.6);    // taille d'une unité de la grille, en pixels
            $angle = self::hasard(-0.35, 0.35);   // rotation, en radians (environ ±20°)
            $cx = 10 + $pas * ($i + 0.5) + self::hasard(-3, 3);    // centre du caractère
            $cy = $h / 2 + self::hasard(-4, 4);
            foreach (self::POLICE[$caractere] as $trait) {
                $d = [];
                for ($k = 0; $k < count($trait); $k += 2) {
                    // point de la grille, centré sur (2, 3), déformé, tourné, placé
                    $x = ($trait[$k] - 2 + self::hasard(-0.2, 0.2)) * $echelle;
                    $y = ($trait[$k + 1] - 3 + self::hasard(-0.2, 0.2)) * $echelle;
                    $px = $cx + $x * cos($angle) - $y * sin($angle);
                    $py = $cy + $x * sin($angle) + $y * cos($angle);
                    $d[] = sprintf('%s%.1f %.1f', $k === 0 ? 'M' : 'L', $px, $py);
                }
                $morceaux[] = sprintf('<path d="%s" fill="none" stroke="%s" stroke-width="%.1f" '
                    .'stroke-linecap="round" stroke-linejoin="round"/>',
                    implode(' ', $d), self::couleur(), self::hasard(2.2, 3));
            }
        }

        // 3 traits de brouillage : des courbes qui traversent l'image
        for ($n = 0; $n < 3; $n++) {
            $morceaux[] = sprintf('<path d="M%.1f %.1f C%.1f %.1f %.1f %.1f %.1f %.1f" fill="none" '
                .'stroke="%s" stroke-width="1.3"/>',
                self::hasard(0, 20), self::hasard(5, 45), self::hasard(30, 60), self::hasard(0, 50),
                self::hasard(90, 120), self::hasard(0, 50), self::hasard(130, 150), self::hasard(5, 45),
                self::couleur());
        }
        $morceaux[] = '</svg>';
        return implode('', $morceaux);
    }

// src/Securite/CaptchaService.php : les captchas en attente, gardés par le serveur,
// dans le cache (cf. exemple 20)

namespace App\Securite;

use Psr\Cache\CacheItemPoolInterface;

class CaptchaService
{
    // la durée de vie d'un captcha, en secondes
    private const DUREE_VIE = 600;

    public function __construct(private CacheItemPoolInterface $cache)
    {
    }

    public function generer(): Captcha
    {
        $texte = DessinCaptcha::texteAleatoire(5);
        // un identifiant aléatoire, impossible à deviner : 12 octets tirés par un
        // générateur cryptographique (random_bytes), écrits en hexadécimal (bin2hex)
        $id = bin2hex(random_bytes(12));
        // la réponse attendue, dans le cache, pour 10 minutes (expiresAfter) : le
        // cache l'oubliera de lui-même ensuite
        $element = $this->cache->getItem("captcha.$id");
        $this->cache->save($element->set($texte)->expiresAfter(self::DUREE_VIE));
        return new Captcha($id, DessinCaptcha::svg($texte));
    }

    // le captcha est CONSOMMÉ dans tous les cas : une image ne sert qu'une fois
    public function verifier(?string $id, ?string $saisie): bool
    {
        // un identifiant mal formé ne peut pas être une clé du cache
        if ($id === null || ! ctype_xdigit($id) || $saisie === null) {
            return false;
        }
        $element = $this->cache->getItem("captcha.$id");
        // deleteItem : la réponse est retirée du cache, qu'elle soit bonne ou non
        $this->cache->deleteItem("captcha.$id");
        if (! $element->isHit()) {
            return false;    // identifiant inconnu, ou captcha expiré
        }
        // strcasecmp rend 0 pour deux chaînes égales, majuscules et minuscules confondues
        return strcasecmp($element->get(), trim($saisie)) === 0;
    }
}
    • lignes 18-29 : un nouveau captcha : un texte aléatoire, un identifiant aléatoire et impossible à deviner, et le dessin. Le serveur garde, pour chaque identifiant, la réponse attendue, dans le cache (exemple 20), pour dix minutes : la méthode [expiresAfter] de l'élément de cache fixe sa durée de vie, en secondes. Passé ce délai, le cache l'oublie de lui-même. La page ne reçoit que l'identifiant et l'image : la réponse ne quitte jamais le serveur ;
    • lignes 32-46 : la vérification. L'identifiant vient du client : on vérifie d'abord qu'il est fait de chiffres hexadécimaux ([ctype_xdigit]), car certains caractères ([{}()/\@:]) sont interdits dans les clés du cache, qui lèverait une exception. L'élément est lu, puis retiré du cache ([deleteItem]) : le captcha est consommé dans tous les cas, réussi ou non. Sans cela, un programme pourrait essayer toutes les réponses sur une même image. La comparaison ignore la casse ([strcasecmp] rend 0 pour deux chaînes égales, majuscules et minuscules confondues) et les espaces autour de la saisie ([trim]).

namespace App\Controller;

use App\Securite\AuthService;
use App\Securite\CaptchaService;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Exception\AccessDeniedHttpException;
use Symfony\Component\RateLimiter\RateLimiterFactoryInterface;
use Symfony\Component\Routing\Attribute\Route;

class AuthController extends AbstractController
{
    // $loginLimiter : la fabrique du limiteur [login] (cf. config/packages/framework.yaml) ;
    // le nom du paramètre désigne le limiteur
    public function __construct(
        private AuthService $auth,
        private CaptchaService $captchas,
        private RateLimiterFactoryInterface $loginLimiter,
    ) {
    }

    #[Route('/', methods: ['GET'])]
    public function accueil(): Response
    {
        return $this->redirect('/profil');
    }

    #[Route('/login', methods: ['GET'])]
    public function formulaire(): Response
    {
        return $this->pageLogin();
    }

    #[Route('/login', methods: ['POST'])]
    public function connexion(Request $request): Response
    {
        $saisies = $request->getPayload();
        if (! $this->isCsrfTokenValid('login', $saisies->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('jeton anti-CSRF invalide');
        }
        $login = $saisies->getString('login');
        // le limiteur de CE client : son compteur d'échecs a pour clé son adresse IP
        $limiteur = $this->loginLimiter->create($request->getClientIp());

        // 1. une adresse bloquée n'est même pas écoutée ; consume(0) consulte le
        // compteur sans rien consommer
        $etat = $limiteur->consume(0);
        if ($etat->getRemainingTokens() === 0) {
            $secondes = $etat->getRetryAfter()->getTimestamp() - time();
            return $this->pageLogin($login, "Trop de tentatives : réessayez dans $secondes s.");
        }
        // 2. le captcha d'abord (peu coûteux), le mot de passe (bcrypt, coûteux) ensuite ;
        // consume() : un échec de plus
        if (! $this->captchas->verifier($saisies->getString('captchaId'), $saisies->getString('captcha'))) {
            $limiteur->consume();
            return $this->pageLogin($login, "Le code de l'image est incorrect.");
        }
        $utilisateur = $this->auth->valider($login, $saisies->getString('motDePasse'));
        if ($utilisateur === null) {
            $limiteur->consume();
            return $this->pageLogin($login, 'Login ou mot de passe incorrect.');
        }
        // une connexion réussie efface les échecs
        $limiteur->reset();
        $reponse = $this->redirect('/profil');
        $reponse->headers->setCookie(Cookie::create(AuthService::COOKIE, $this->auth->creerJeton($utilisateur))
            ->withExpires(time() + $this->auth->dureeMinutes * 60)
            ->withHttpOnly(true)
            ->withSameSite(Cookie::SAMESITE_LAX));
        return $reponse;
    }

    #[Route('/logout', methods: ['POST'])]
    public function deconnexion(Request $request): Response
    {
        if (! $this->isCsrfTokenValid('logout', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('jeton anti-CSRF invalide');
        }
        $reponse = $this->redirect('/login');
        $reponse->headers->clearCookie(AuthService::COOKIE);
        return $reponse;
    }

    // chaque affichage du formulaire fabrique un NOUVEAU captcha
    private function pageLogin(?string $login = null, ?string $erreur = null): Response
    {
        return $this->render('auth/login.html.twig', ['login' => $login, 'erreur' => $erreur,
            'captcha' => $this->captchas->generer()]);
    }
}
    • lignes 21-26 : le contrôleur reçoit la fabrique du limiteur [login] ;
    • ligne 49 : le limiteur de ce client : [create(clé)] rend un limiteur qui a son propre compteur, sous cette clé, ici l'adresse IP du client ([getClientIp()]) ;
    • lignes 53-57 : une adresse bloquée n'est même pas écoutée. [consume(0)] consulte le limiteur sans rien consommer ; l'objet [RateLimit] qu'il rend donne le nombre de jetons restants ([getRemainingTokens()]) et la date à laquelle l'action sera de nouveau permise ([getRetryAfter()]), dont on déduit le nombre de secondes à attendre ;
    • lignes 60-68 : le captcha est vérifié avant le mot de passe : sa vérification ne coûte presque rien, alors que [bcrypt] est volontairement lent. Un programme qui se tromperait de captcha ne ferait ainsi pas travailler [bcrypt]. Chaque échec, de captcha ou de mot de passe, consomme un jeton ([consume()], qui en consomme un par défaut). Au troisième échec, il n'en reste plus : l'adresse est bloquée jusqu'à la fin de la fenêtre de 60 secondes, comptées depuis le premier échec ;
    • ligne 70 : une connexion réussie efface les échecs ([reset()]) ;
    • lignes 91-95 : chaque affichage du formulaire fabrique un nouveau captcha, y compris après un échec.

    Le SecurityBundle offre aussi une limitation intégrée des connexions (l'option [login_throttling] du pare-feu), qui s'applique à ses propres authentificateurs de connexion ([form_login]...), et non à notre action. Pour limiter le nombre de requêtes d'une route, on utiliserait un limiteur de la même façon, dans l'action ou dans un écouteur de [kernel.request]. Nous avons préféré compter les seuls échecs, pour ne pas gêner un utilisateur qui se connecte normalement.
